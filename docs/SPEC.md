# Маяк: открытая карта сетевой доступности

*Архитектура и ТЗ · версия 0.2 · 13 октября 2026 · «Маяк» — рабочее название*

## 1. Суть и границы

Система отвечает на вопрос: «у меня одного не открывается сервис или у всего моего оператора, и по какой причине?» Состоит из трёх частей:

- **Агент** — CLI/демон, который измеряет, что именно ломается на пути до сервиса.
- **Сервер** — принимает добровольные отчёты и считает статус по паре «оператор (ASN) × сервис».
- **Публичный слой** — API, статичная страница статуса, Telegram-бот, экспорт открытых данных.

**Цели:** локальная диагностика, полезная без какой-либо отправки; агрегированная карта; открытый формат отчёта, который могут использовать чужие проекты.

**Не цели:** обход блокировок (только измерение); сбор данных о людях и их трафике; рейтинг «хороших» и «плохих» провайдеров; проверка произвольных сайтов по запросу (список целей курируется).

## 2. Принципы

1. **Согласие.** Отправка выключена по умолчанию; перед отправкой показывается точный JSON.
2. **Минимум данных.** Только страна, цель, результат, время. Ни IP, ни идентификатора установки в отчёте нет.
3. **Честная неопределённость.** «Мало данных» — полноценный статус, а не ошибка.
4. **Малая нагрузка.** Жёсткие потолки по соединениям и частоте, джиттер, пауза на батарее.
5. **Проверяемость.** Открытый код, подписанные релизы, версионируемая схема.
6. **Только публичные популярные цели**, у каждой записано обоснование.

## 3. Пользователи и сценарии

| Роль | Что нужно | Как получает |
| --- | --- | --- |
| Рядовой пользователь | Понять, в чём причина | Веб-проба, Telegram-бот |
| Энтузиаст, самохостер | Глубокая диагностика, участие в карте | CLI, Docker, пакет для OpenWrt |
| Автор инструмента или списков | Сигнал «у оператора X сейчас режется Y» | Public API, экспорт, webhooks |

## 4. Архитектура

```
Агент (CLI/демон) ──┐
Веб-проба (JS) ─────┼─▶ Ingest API ─▶ Очередь ─▶ Валидатор + Enricher ─▶ PostgreSQL
                    │        ▲                                             │
Контрольный узел ◀──┘        │ цели и ключи (подписаны)                    ▼
(вне фильтруемой зоны)   Targets API                                    Агрегатор
                                                              (окна, кворум, CUSUM)
                                                                          │
                         Public API ◀─────────────────────────────────────┘
                              │
                 ┌────────────┼─────────────┐
            Страница      Telegram-бот   Экспорт / webhooks
            статуса
```

| Компонент | Задача |
| --- | --- |
| `mayak` (агент) | Тесты, классификация, согласие, отправка |
| `mayakd` (сервер) | Один бинарник: ingest, targets, public API, агрегатор (роли включаются флагами) |
| Контрольный узел | Эхо-эндпоинты вне фильтруемой зоны: TLS с любым SNI, UDP/QUIC, HTTP-эхо с хэшем тела. Нужен, чтобы отличить блокировку от «просто упало». Протокол: см. §21 |
| PostgreSQL | Сырые отчёты (короткий срок), агрегаты (долгий) |
| Статика и бот | Генерируются из Public API, своей логики не содержат |

Развёртывание: `docker compose` из `mayakd`, PostgreSQL и Caddy; контрольный узел — отдельный VPS в другой юрисдикции.

## 5. Агент

```
mayak check [--targets core] [--json]   # локальная диагностика, ничего не отправляет
mayak report --dry-run                  # показать, что было бы отправлено
mayak run [--interval 30m] [--share]    # демон; --share = явное согласие на отправку
mayak consent grant|revoke|status
mayak selfupdate                        # только с проверкой подписи релиза
```

**Ограничения нагрузки:** не более 4 одновременных проверок; пауза 200–800 мс между ними; таймаут 8 с на тест; интервал демона 30 минут со случайным сдвигом ±20%; 5–20 целей за прогон с ротацией; без отправки на батарее и в лимитных сетях.

**Список целей** приходит с сервера как JSON, подписанный ed25519 (открытый ключ вшит в агент). Поля: `id`, `host`, `category` (`ai`, `video`, `messenger`, `dev`, `social`, `infra`), `rationale`, `rev`. Новая цель добавляется через PR с обоснованием: публичный сервис и массовая аудитория.

### Тесты

| ID | Что делает | Что выявляет |
| --- | --- | --- |
| `dns` | Сравнивает ответы системного резолвера, двух публичных DoH/DoT и контрольного узла | Подмену ответа, NXDOMAIN-инъекцию, заглушки (private/bogon IP) |
| `tcp` | TCP connect к IP:443 (IP из доверенного ответа) | Блок по IP: таймаут или RST на SYN |
| `tls_sni` | Два handshake на один IP: с SNI цели и с нейтральным SNI | SNI-фильтрацию (обрыв после ClientHello только в первом случае), подмену сертификата |
| `http` | GET небольшого пути; статус, размер и хэш тела сравниваются с эталоном контрольного узла | Страницы-заглушки; отличает блок сети от отказа самого вендора |
| `quic` | QUIC Initial на UDP/443 | Блок QUIC/HTTP3 |
| `rst_ttl` (этап 5, нужен root) | Пассивно сравнивает TTL RST-пакетов с TTL обычных пакетов сервера | Инъекцию RST «посередине» |
| `ctrl` | Доступность контрольного узла и 2–3 заведомо живых опорных сайтов | Если не прошёл, весь прогон считается `inconclusive` |

### Вердикты и правила

Вердикты: `ok`, `dns_tamper`, `ip_block`, `sni_block`, `tls_intercept`, `http_stub`, `quic_block`, `vendor_geoblock`, `timeout_unknown`, `inconclusive`.

1. `ctrl` не прошёл → `inconclusive`, в агрегат такой результат не идёт.
2. Ответы DNS расходятся, а системный указывает на private/bogon или на IP, которого нет у остальных → `dns_tamper`; дальнейшие тесты идут по доверенному IP.
3. `tcp` в таймауте при живом `ctrl` → `ip_block`.
4. Handshake с SNI цели обрывается, а с нейтральным SNI на тот же IP проходит → `sni_block`.
5. Сертификат не валиден для цели → `tls_intercept`.
6. Handshake прошёл, но тело — заглушка (отличается от эталона и совпадает с известной заглушкой оператора) → `http_stub`.
7. Handshake и сертификат корректны, но вендор отвечает отказом по региону (403/451 с его собственной страницей) → `vendor_geoblock`. К сети это не относится и показывается отдельно.

## 6. Веб-проба

Страница без установки: `fetch(url, {mode: 'no-cors'})`, загрузка `<img>`/`<script>` и WebSocket с замером времени. Браузер видит только «доступно / нет» и грубую задержку, причину отличить не может. Такие отчёты помечаются `source: web` и весят в агрегате меньше. Результат показывается пользователю сразу, а в общую карту уходит только по явной галочке.

## 7. Формат отчёта (`mayak.report/1`)

```json
{
  "schema": "mayak.report/1",
  "report_id": "b7c1e0a4f2",
  "ts": "2026-10-13T12:30:00Z",
  "agent": {"ver": "0.3.1", "os": "linux/arm64", "source": "cli"},
  "net": {"ip_ver": 4, "resolver": "isp", "country": "RU", "region": null},
  "targets_rev": "2026-10-12.1",
  "results": [
    {"target": "example-ai-api", "test": "tls_sni", "verdict": "sni_block",
     "evidence": {"ctrl_sni_ok": true, "target_sni_err": "reset_after_hello", "ms": 212}}
  ]
}
```

**Правила приватности:**

- ASN и страну сервер определяет по IP соединения во время приёма и сразу забывает IP; агент их не отправляет. Регион (субъект РФ) указывается только если пользователь задал его сам.
- `report_id` случаен для каждого отчёта: связать два отчёта одного агента нельзя.
- Время округляется до 5 минут.
- Размер отчёта не больше 64 КБ, поля вне схемы отбрасываются.
- `evidence` содержит только технические признаки (тип ошибки, тайминги), без тел ответов и сертификатов целиком.

## 8. Приём отчётов (Ingest API)

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/v1/targets` | Подписанный список целей |
| GET | `/v1/control` | Адреса и параметры контрольного узла |
| GET | `/v1/pow` | Задача proof-of-work (hashcash) |
| POST | `/v1/reports` | Приём отчёта |
| GET | `/v1/status` | Статус по ASN и цели |
| GET | `/v1/events` | События смены статуса (SSE) |
| GET | `/v1/export/{asn}.json` | Выгрузка по оператору |

**Конвейер приёма:**

1. Caddy терминирует TLS; формат лога без `remote_addr`, IP живёт только в памяти обработчика.
2. Проверка PoW и лимитов.
3. Валидация по JSON Schema, лимит 64 КБ, неизвестные поля отбрасываются.
4. Enricher: IP → ASN и страна по локальной базе, затем IP отбрасывается. Для подсчёта разных источников считается `src_bucket = H(salt_day ‖ prefix)`, где prefix — это /24 для IPv4 или /56 для IPv6, а соль меняется каждые сутки и стирается через 48 часов. Так в окне можно посчитать число независимых источников, но нельзя отслеживать человека во времени.
5. Запись в очередь. На MVP это таблица в Postgres и `LISTEN/NOTIFY`, без Kafka.
6. Ответ `202`.

Коды ответов: `202` принят, `400` не прошла схема, `409` повтор `report_id` (идемпотентность), `413` слишком большой, `429` лимит. Лимиты: не более 6 отчётов в час с одного `src_bucket`, глобальный потолок на ASN, сложность PoW растёт с нагрузкой.

## 9. Агрегатор и детектор

Единица агрегации: ключ `(asn, target, test_family)`. Окна: скользящий час и сутки.

```
for r in results(key, window):
    w     = 1.0 if r.source == 'cli' else 0.3        # веб-проба весит меньше
    w     = min(w, cap_per_bucket(r.src_bucket))      # один источник <= 20% веса окна
    decay = 0.5 ** (age(r) / HALF_LIFE)               # HALF_LIFE = 3h, как «забывание» в Nova
    if reachable(r): alpha += w * decay
    elif counts_as_network_failure(r): beta += w * decay

n_eff = alpha + beta
p     = (alpha + 1) / (alpha + beta + 2)             # Beta(1,1) prior
```

**Состояния:**

| Состояние | Условие |
| --- | --- |
| `unknown` | `n_eff < 3` или меньше 2 разных `src_bucket` |
| `ok` | `p >= 0.85` |
| `degraded` | `0.40 <= p < 0.85` |
| `blocked` | `p < 0.40` при достаточной выборке |

Вход в состояние и выход из него идут по разным порогам (гистерезис ±0.05), чтобы статус не дребезжал. Причина (`top_cause`) — взвешенная мода вердиктов среди неудач; если доля лидера меньше 60%, причина `mixed`.

**Детектор смены режима:** CUSUM по доле неудач на ключ; событие `status_change` публикуется, когда CUSUM сработал и новое состояние подтвердилось в двух соседних окнах.

**Защита от отравления:**

- вклад одного `src_bucket` ограничен 20% веса окна;
- веб-источник сам по себе не может перевести ключ в `blocked`;
- при 5 и более источниках берётся медиана по `src_bucket`, а не среднее;
- `vendor_geoblock` и `inconclusive` не считаются сетевой недоступностью;
- на публичной странице видны число источников и давность данных.

## 10. Хранилище

```sql
CREATE TABLE results (
  ts         timestamptz NOT NULL,
  asn        int         NOT NULL,
  country    text        NOT NULL,
  src_bucket bytea       NOT NULL,   -- H(salt_day || prefix), соль стирается через 48ч
  source     text        NOT NULL,   -- cli | web
  target_id  text        NOT NULL,
  test       text        NOT NULL,
  verdict    text        NOT NULL,
  evidence   jsonb
) PARTITION BY RANGE (ts);          -- партиция на сутки, хранить 14 суток

CREATE TABLE status_agg (
  asn int, target_id text, ts_hour timestamptz,
  alpha real, beta real, n_eff real, state text, top_cause text,
  PRIMARY KEY (asn, target_id, ts_hour)
);                                  -- хранить 12 месяцев

CREATE TABLE events (
  id bigserial PRIMARY KEY, ts timestamptz,
  asn int, target_id text, old_state text, new_state text, cause text
);
```

**Оценка нагрузки:** 500 проб × 10 целей × 5 тестов × 2 прогона в час ≈ 50 тыс. строк в час, около 1,2 млн в сутки. Для Postgres это комфортно, TimescaleDB и ClickHouse на старте не нужны.

## 11. Публичный слой

- **Public API:** только чтение, кэш 60 секунд, открытый CORS. Лицензия данных — CC0 или ODbL (см. раздел 16).
- **Страница статуса:** статика, пересобирается раз в минуту из `/v1/status`. Матрица «операторы × сервисы», в ячейке состояние или «мало данных». Работает без JS.
- **Telegram-бот:** `/status <оператор> <сервис>`; `/why` разбирает присланный вывод `mayak check --json`; `/watch` подписывает на события.
- **Экспорт:** JSON по оператору и простые списки доменов в состоянии `blocked` (по строке на домен) для чужих инструментов.
- **Webhooks:** подписка на события `status_change` по ASN и цели.

## 12. Безопасность и модель угроз

| Угроза | Мера |
| --- | --- |
| Отравление данных ложными «заблокировано» | Потолок веса источника, кворум, PoW, малый вес веб-пробы, публичная статистика аномалий |
| DoS на приём | PoW, лимиты по префиксу, дешёвая валидация до записи, кэш на чтение |
| Деанонимизация | IP не пишется, `src_bucket` с суточной солью, округление времени, нет идентификатора установки, логи без адресов |
| Давление на оператора сервера | Минимум хранимого: нечего выдавать сверх агрегатов и 14 дней обезличенных строк; хостинг в удобной юрисдикции |
| Подмена списка целей или обновления | Подпись ed25519, подписанные релизы (minisign или cosign), воспроизводимая сборка |
| Агент как сканер | Только курируемый список, нет произвольных целей, потолки нагрузки |
| Компрометация контрольного узла | В нём нет секретов, он лишь отдаёт эхо; запас доменов и ротация |

**Этика и право.** Агент только измеряет доступность публичных сервисов: он ничего не обходит и не учит обходу. Юридические риски стоит оценить отдельно для вашей юрисдикции и хостинга; я не юрист, и этот раздел не заменяет консультацию.

## 14. Тестирование

Главный инструмент — **мок-цензор** `testbed/mockdpi`: прокси на TCP и UDP, который по YAML-профилю имитирует блокировки. Он обрывает соединение после ClientHello с заданным SNI, подменяет DNS-ответ, отдаёт заглушку, роняет UDP/443, молчит на SYN. Благодаря ему классификатор проверяется детерминированно, без реальной цензуры и прямо в CI.

- **Unit:** классификатор на таблицах «сырые наблюдения → вердикт» (golden-тесты).
- **Integration:** агент против мок-DPI и контрольного узла в docker-сети.
- **Агрегатор:** симуляция потока отчётов из честных источников и атакующего; проверка, что статус не переключается.
- **Fuzz:** валидатор отчётов.
- **Приватность:** интеграционный тест, который грепает логи и БД на IP-адрес тестового клиента и падает, если находит.
- **Нагрузка:** 5 тыс. отчётов в минуту на ingest.

## 16. Открытые вопросы

1. Лицензия данных (CC0 или ODbL) и кода (MIT или Apache-2.0 для агента; для сервера возможен AGPL).
2. Источник базы ASN с подходящей лицензией.
3. Где разместить контрольный узел; для независимости нужно минимум два в разных сетях.
4. Когда оправданы анонимные токены вместо PoW.
5. Нужен ли региональный разрез (субъект РФ) и как получать его без деанонимизации.
6. Юридическая оценка рисков в вашей юрисдикции.

## 17. Как вайбкодить этот проект

1. Положите документ в репозиторий как `docs/SPEC.md` и заведите `AGENTS.md`: версия Go, стиль, запрет писать IP в логи, обязательные тесты на классификатор.
2. Просите по одному вертикальному срезу: сначала схема и валидатор, потом мок-DPI, потом один тест (`tls_sni`) целиком вместе с классификатором.
3. Каждый раз требуйте сначала тест на мок-DPI, потом код.
4. На каждое решение пишите ADR с отвергнутыми альтернативами, как в Nova.
5. Приватность проверяйте тестом, а не обещанием.

## 18. Анонимность v2: токены и учётные данные вместо PoW

*Добавлено по комментарию к разделу 12. Раздел заменяет PoW и `src_bucket` из разделов 8–9 в целевой архитектуре; M5 из плана становится обязательным для публичного запуска.*

**Требование:** сервер не должен ни связывать отчёты одного агента, ни видеть его IP, а защита от спама и взвешивание источников при этом должны работать.

### Три слоя

**1. Сетевой слой.** Отправка через Oblivious HTTP (RFC 9458): релей видит IP, но не содержимое; шлюз видит содержимое, но не IP. Альтернатива — onion-сервис Tor. Цена: сервер больше не определяет ASN по IP. Либо агент заявляет ASN сам (проверить это нечем), либо релей приписывает ASN заголовком, и тогда нужно доверять оператору релея, отдельному от оператора шлюза.

**2. Антиспам: анонимные токены.** Privacy Pass-подобная схема (слепая подпись, RFC 9578, или VOPRF, RFC 9497). При выдаче агент получает пачку токенов на эпоху (например, неделю) и тратит по одному на отчёт. Токен нельзя связать с выдачей. Единственное место, где виден IP, — выдача, поэтому именно там стоит сильный барьер: PoW, лимит по префиксу, опционально инвайт.

**3. Возраст пробы.** Слепая подпись сама по себе не несёт скрытого атрибута, поэтому возможны два пути.

| Вариант | Как работает | Плюсы и минусы |
| --- | --- | --- |
| **A. Лесенка возраста** | Токен несёт когорту (0–1, 2–7, 8+ недель). Для новой эпохи агент предъявляет токен прошлой эпохи, сервер гасит его и выдаёт токены следующей когорты вслепую | Без ZK, просто, но нельзя посчитать независимые источники |
| **B. Анонимные учётные данные + ZK** | Credential с атрибутом `issued_epoch` (BBS или keyed-verification, как в CMZ). Агент неинтерактивным (Fiat–Shamir) доказательством показывает «возраст ≥ k» и нулификатор `PRF(sk, epoch, target, window)` | Точный возраст, лимит «один отчёт на цель в окно», подсчёт независимых источников; сложнее и тяжелее |

Рекомендация пересмотрена: вариант A отклонён (см. раздел 19 и ADR-005); целевой путь — Privacy Pass на M4.5 и учётные данные на M7. Перед реализацией B сверьтесь с актуальными публикациями OONI по анонимным учётным данным: деталей их схемы я не помню и не хочу выдавать догадки за описание.

### Что ZK не решает

- **Sybil.** Доказательство делает пробу анонимной, но не делает её уникальной: оно переносит проблему на этап выдачи. Поэтому вес возраста ограничен сверху (например, множитель не выше 1,5), а статус по ASN по-прежнему требует кворума, а не суммы весов.
- **Подсчёт источников.** Без нулификатора (вариант A) мы теряем «число независимых проб в окне». Остаётся лимит токенов на эпоху и нижняя оценка: отчётов не больше, чем токенов × число проб. В B нулификатор на пару «цель × окно» возвращает честный подсчёт.
- **Размер анонимного множества.** Если в ASN три пробы, то пара «ASN + время» уже почти идентификатор. Поэтому публикуем статус только от 5 источников, округляем время, отправляем со случайной задержкой, укрупняем поля вроде версии агента и типа резолвера.

### Изменения в остальных разделах

- **Раздел 8:** шаг 2 (PoW и лимиты) заменяется проверкой токена; шаг 4 теряет `src_bucket`, вместо него сохраняются возрастная когорта и эпоха.
- **Раздел 9:** вес `w` умножается на `age_factor(cohort)`; потолок вклада источника строится на нулификаторах (B) или на токенах эпохи (A).
- **Раздел 12:** в «Деанонимизации» добавляется «сервер не видит IP при OHTTP» и «отчёты не связываются через токены».
- **План:** M5a — OHTTP и токены (вариант A); M5b — учётные данные и нулификаторы (вариант B).

## 21. Версия 0.3: протокол контрольного узла, формат списка целей v2, перечни полей отчёта

*14 октября 2026. Приоритет выше разделов 19 и 20. Раздел описывает то, что реализовано в коде (`internal/probe/control.go`, `internal/targets`, `internal/report`, `schema/report.schema.json`) после доработок по ревью. Где написано «требование к `mayak-ctrl`», узла ещё нет: это условие, которое код узла обязан выполнять, а не описание существующего кода. Старые разделы не правятся; при расхождении действует этот раздел.*

### 21.1 Контрольный узел (раздел 4)

Клиент называет только имя цели. Он никогда не передаёт IP-адрес или порт: узел сам находит адреса и сам подключается, поэтому им нельзя просканировать произвольный адрес.

| Запрос | Ответ |
| --- | --- |
| `GET /v1/ping` | `200`, если узел жив |
| `GET /v1/reach?host=<host>` | `200 {"reachable": bool}`: узел пробует TCP-соединение с хостом на порт 443 снаружи фильтруемой зоны |
| `GET /v1/fetch?host=<host>&path=<path>` | `200 {"status": int, "size": int, "body_hash": "<hex sha-256>"}`: узел делает тот же запрос, что тест `http` (HTTPS на порт 443 с SNI `host`, без редиректов, не больше 1 МиБ тела, тело в том виде, в каком его получает HTTP-клиент агента, то есть после распаковки), и описывает ответ. Любой другой статус значит «не смог» |

**Путь.** `path` принимает только два значения: `/` и `/robots.txt`. Клиент (`ControlClient.Reference`) отказывает любому другому пути ошибкой `ErrBadControlPath` до сетевого запроса. Путь статичный, иначе хеши тел агента и узла расходятся.

**Требования к `mayak-ctrl`** (клиент их проверить не может):

- Обслуживает только хосты из своей копии подписанного списка целей (проверенной так же, как это делает агент, см. 21.2). Любой другой хост отклоняется.
- Подключается только к порту 443 и только к публичным адресам: никаких private, loopback, link-local, CGNAT и других bogon-адресов, что бы ни вернул резолвер. Проверяется адрес, к которому узел реально подключается.
- Не принимает и отклоняет запросы с параметрами `ip` и `port`.
- Ограничивает частоту запросов и размер забираемого тела (1 МиБ).
- Не логирует адреса клиентов (ADR-004: политика «без логов», тест «IP не оседает»).

**Следствие.** Взгляд узла «снаружи» может идти на другой узел CDN, чем у агента, поэтому расхождение его ответа с ответом агента не доказательство блокировки само по себе. Тест `ctrl` считает контрольный узел живым, если он ответил на `/v1/ping`, а опорный сайт живым, если он ответил статусом ниже 500; достаточно одного живого опорного сайта.

### 21.2 Список целей, формат v2 (разделы 5 и 12)

**Файл.** `{"payload": "<base64 точных байт JSON>", "sig": "<base64 ed25519>"}`. Подпись считается над байтами payload ровно как они лежат в файле. Агент сначала проверяет подпись одним из вшитых ключей (`internal/targets/pubkeys.go`) и только потом разбирает JSON; ничего не сериализуется заново, поэтому порядок полей и пробелы не важны, а любой изменённый байт ломает подпись.

**Содержимое payload.** `v` (версия формата, сейчас 1), `rev`, `expires`, `items`. Цель: `id`, `host`, `category` (`ai`, `video`, `messenger`, `dev`, `social`, `infra`), `rationale` (не короче 20 символов), `rev`.

- **Версия и неизвестные поля.** Агент игнорирует поля payload, которых не знает (они подписаны), но отклоняет `v` больше известной (`ErrUnsupportedVersion`) и отсутствующий `v`. Подписывающий инструмент, наоборот, отказывается подписывать неизвестные поля, чтобы не подписать опечатку.
- **`host`.** Только DNS-имя: ASCII, нижний регистр, метки 1–63 символа из `a-z0-9-` без дефиса по краям, не больше 253 символов, не меньше двух меток, юникод только в punycode. Отклоняются IP-адреса, порт, путь, `?`, `#`, `@`, `*`, пробелы, схема, точка в конце, внутренние зоны (`localhost`, `.local`, `.internal`, `.lan`, `.home.arpa`, `.test`, `.invalid`) и дубликаты `host` и `id` в одном списке.
- **Срок действия.** Подписывается список с `expires` не в прошлом и не дальше 30 дней от момента подписи; допусков при подписи нет. Рекомендуется `expires` ≈ +28 дней. Агент отклоняет истёкший список (`expires` не позже его часов; допуска нет) и список с `expires` дальше 30 дней от его часов, но ко второй проверке у него допуск 10 минут (`ClockSkew`) на часы, отстающие от часов подписанта.
- **Откат.** `rev` имеет вид `ГГГГ-ММ-ДД.N` (`N` от 1 до 4 цифр). Сравниваются сначала дата, потом `N` как число (`.10` новее `.9`). Агент хранит последний принятый `rev` и отклоняет меньший (`ErrRollback`); тот же `rev` допустим. Порядок: проверка подписи и срока, затем сверка с сохранённым, затем запись нового (`Accept`). Если новый `rev` записать не удалось, список не принимается. Повреждённый файл с `rev` не сбрасывается молча, это ошибка, потому что сброс стёр бы защиту от отката. Файл создаётся с правами 0600 в каталоге 0700, запись атомарная; путь передаёт вызывающий. По решению владельца в `cmd/mayak` это `os.UserConfigDir()/mayak/targets.rev` (в `cmd/mayak` пока не подключено).
- **Подписывающий инструмент** (`cmd/mayak-sign`, см. `docs/KEYS.md`) берёт `rev` и `expires` из входного файла и не перезаписывает в `--out` список с таким же или большим `rev`.
- **Смена ключа.** В три шага: сначала в агент добавляется второй открытый ключ и выходит релиз, потом список подписывается новым ключом, потом старый ключ удаляется. При утечке старый ключ не остаётся в списке доверенных, а заменяется (подробно в `docs/KEYS.md`).
- **Защита релиза.** Строка вшитого ключа с меткой `// TESTKEY` блокирует `make release-check` (CI запускает его на тегах `v*`). `make sign-check` проверяет, что `targets/targets.signed.json`, если он есть, подписан вшитым ключом и соответствует формату; срок действия он не проверяет.

### 21.3 Отчёт `mayak.report/1` (раздел 7)

Значения полей, которые принимает валидатор (`internal/report`, зеркало в `schema/report.schema.json`):

| Поле | Допустимо |
| --- | --- |
| `schema` | `mayak.report/1` |
| `report_id` | 10 строчных hex-символов |
| `ts` | RFC 3339; сервер округляет вниз до 5 минут (UTC) |
| `agent.ver` | `major.minor` (по 1–3 цифры) или `dev` |
| `agent.os` | `linux`, `windows`, `darwin`, `android`, `ios`, `openwrt`, `other` (только семейство, без версии и архитектуры) |
| `agent.source` | `cli`, `web` |
| `net.ip_ver` | `4` или `6` |
| `net.resolver` | `isp`, `public`, `encrypted`, `vpn`, `unknown` |
| `net.country` | две заглавные буквы или пусто (по разделу 7 страну определяет сервер, агент её не отправляет) |
| `net.region` | `null` или код вида `RU-MOW` (две заглавные буквы, дефис, 1–3 заглавные буквы или цифры); только если пользователь задал его сам |
| `targets_rev` | `ГГГГ-ММ-ДД.N`, `N` от 1 до 4 цифр |
| `results` | от 1 до 200 элементов |
| `results[].target` | `a-z`, `0-9`, `-`, длина 1–64 (по смыслу `id` цели из списка) |
| `results[].test` | `dns`, `tcp`, `tls_sni`, `http`, `quic`, `tcp_freeze`, `throughput`, `ctrl` |
| `results[].verdict` | `ok`, `dns_tamper`, `ip_block`, `sni_block`, `tls_intercept`, `http_stub`, `quic_block`, `vendor_geoblock`, `timeout_unknown`, `inconclusive`, `vendor_down`, `allowlist_mode`, `freeze_after_n`, `throttled` (для двух последних правил классификатора пока нет) |
| `results[].evidence` | только технические признаки; строки не длиннее 200 символов; вложенность не глубже двух уровней (сам объект `evidence` первый уровень) |

Размер отчёта не больше 64 КБ; поля вне схемы отбрасываются. Пример в разделе 7 устарел в двух полях: `agent.ver` теперь `major.minor` (не `0.3.1`), `agent.os` только семейство (не `linux/arm64`).

**Приём.** Сервер проверяет отчёты только функцией `ValidateAt`: она делает все проверки выше и отклоняет `ts` старше 24 часов или опережающий часы сервера больше чем на 5 минут. Функция `Validate` без часов предназначена для тестов и локальной проверки. Для ответов раздела 8 это даёт `413` для отчёта больше 64 КБ и `400` для остальных нарушений.
