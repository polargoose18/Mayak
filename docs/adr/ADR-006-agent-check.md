# ADR-006: Команда `mayak check`: вывод, коды выхода, файлы, список целей, тесты

**Status:** Accepted (значения по умолчанию плана блока B; владелец не возразил, по Q1 дал ответ; обновлено 2026-11-09)
**Date:** 2026-10-17
**Deciders:** владелец проекта

## Context

Блок B делает `mayak check`: команду, которая на машине пользователя проверяет цели из подписанного списка и показывает вердикты. Всё локально, ничего не отправляется (SPEC §5, этап M1 в §15 и §19). Детали в SPEC не зафиксированы: вид вывода, коды выхода, где агент хранит файлы, откуда берёт список, как тестировать команду, не встраивая тестовые лазейки в бинарник. Ниже решения по вопросам Q1–Q10 плана блока B и разбор того, что SPEC называет «`tls_sni` через контрольный узел».

Источники: SPEC §5 (агент, тесты, вердикты, потолки нагрузки), §19 (решения по ревью, состав M1), §21 (протокол контрольного узла, формат списка целей v2, поля отчёта), ADR-004 (модель угроз).

## Decision

### Q1. Контрольный узел `mayak-ctrl`

Пишется в блоке B (шаг B8), по SPEC §21.1, только на стандартной библиотеке. Агент в блоке B знает ровно один контрольный узел; список из нескольких узлов и запасной способ связи с узлом откладываются на блок C. Развёртывание на VPS не входит в ворота B→C.

Риск, записанный по ответу владельца: имя узла в зоне .ru подчиняется российскому регистратору, его могут снять или заблокировать, а резолвер провайдера может его исказить. Узел должен стоять вне фильтруемой зоны.

### Q2. `tcp_freeze` и `throughput`

Решение владельца от 2026-11-09: перенесены в **блок F**. Причина: вердикты `freeze_after_n`/`throttled` нельзя детерминированно доказать в CI (в `testbed/mockdpi` нет сценария троттлинга, а дропы SYN без firewall не эмулировать), поэтому реализация проб означала бы поставку недостижимого вердикта. Ворота: «перенесены в блок F решением владельца 2026-11-09».

### Q3. Сколько целей и как выбираются

- По умолчанию 10 целей за прогон, флаг `--limit` от 5 до 20 (потолок «5–20 целей за прогон», SPEC §5).
- Выбор по кругу: счётчик ротации хранится в файле `rotation` рядом с `targets.rev` (Q6). За несколько прогонов покрывается весь список, каждая цель один раз за круг.
- Режима «все цели» нет.
- Флаг `--targets` остаётся из SPEC §5, но принимает только значение `core`, и оно означает «весь подписанный список». Категории `core` в формате списка нет (SPEC §21.2), и формат ради неё не меняется.

### Q4. Язык и формат вывода

- Весь вывод только на английском, ASCII, без локалезависимого форматирования, включая сообщения об ошибках. Сырые ошибки Go пользователю не показываются.
- Коды вердиктов (SPEC §21.3) и поля `--json` латиницей и стабильны.
- Вывод по умолчанию: по строке на цель (сервис, вердикт, одно предложение «что это значит»), в конце итог и фраза о том, что ничего не отправлено. Если контрольный узел недоступен, вывод говорит это прямо, а не только «inconclusive».
- `--json` печатает в stdout массив отчётов `mayak.report/1` (SPEC §7, §21.3) и ничего больше. Ошибки идут в stderr. Как результаты прогона раскладываются по отчётам, решает шаг B4.
- Документация проекта остаётся на русском; это решение её не касается.

### Q5. Коды выхода

| Код | Когда |
| --- | --- |
| 0 | Прогон завершён, какие бы ни были вердикты. Вердикт «заблокировано» не ошибка программы |
| 1 | Ошибка запуска или ввода-вывода: неверные флаги, список не принят (истёк, откат, неверная подпись), файлы агента не читаются или не пишутся |
| 2 | Прогону нельзя верить: `ctrl` не прошёл ни на одной цели, то есть все вердикты `inconclusive` |
| 130 | Прогон прерван по Ctrl-C: печатается то, что успело измериться, файлы состояния (`targets.rev`, `rotation`) не трогаются |

Уточнение, принятое при записи: `allowlist_mode` это результат измерения (режим белых списков), а не «нельзя верить», поэтому прогон, где он есть, завершается с кодом 0.

### Q6. Файлы агента

- Каталог `os.UserConfigDir()/mayak/`, права 0700.
- `targets.rev`: последний принятый `rev` (решение уже в SPEC §21.2, реализация `targets.FileRevStore`).
- `rotation`: счётчик ротации (Q3), рядом.
- Оба файла с правами 0600, запись атомарная (временный файл и rename), повреждённый файл не сбрасывается молча, а даёт ошибку с понятным текстом (как `FileRevStore`).
- Пути передаются в код параметрами, а не вшиваются в пакеты; `os.UserConfigDir()` вызывает только `cmd/mayak`.
- На Windows права файлов не проверяются (это записано в рисках плана).

### Q7. Откуда берётся список целей

- По умолчанию встроенная подписанная копия: `go:embed` в отдельном пакете в каталоге `targets/`.
- Флаг `--targets-file` подставляет другой подписанный файл.
- В обоих случаях список проходит `targets.Accept` (подпись вшитым ключом, срок, откат по `targets.rev`; SPEC §21.2). Истёкший список отклоняется с понятным текстом и советом, что делать.
- Загрузки списка по сети в блоке B нет (появится в блоке C). Встроенная копия живёт не больше 30 дней, поэтому перед каждым релизом список переподписывается (пункт чек-листа выхода).
- Флага для произвольного хоста (`--host` и подобных) нет и не будет: агент проверяет только цели из подписанного списка (SPEC §1, §5).

### Q8. Как тестируется команда

- Тесты идут в процессе, через неэкспортируемую функцию создания команды (`newRootCmd()` с подставляемой средой, как в `cmd/mayak-sign`). Среда (`runner.Env`): адреса резолверов, контрольного узла, пул сертификатов, доверенные ключи списка, часы, источник случайности. В тестах туда подставляются адреса `testbed/mockdpi`, его сертификат и тестовый ключ.
- В боевом коде нет ни тестового ключа, ни флагов или переменных окружения для подмены адресов: это была бы лазейка в бинарнике и ловушка для `make release-check`.
- Собранный бинарник проверяется только дымовым тестом: `version`, отказ на истёкшем и на неверно подписанном списке.

### Q9. `mockdpi` не отбрасывает SYN

Для `ip_block` по таймауту connect остаётся юнит-тест с истёкшим дедлайном. Тест с настоящим firewall (network namespace и iptables, нужен root) не входит в блок B, это идея для блока F.

### Q10. Операционные системы

Linux и Windows. macOS отложен решением владельца: в CI его нет, сборки под него нет. В CI сборка и `go test` на обеих ОС с закреплёнными образами, `-race` только на Linux. Формулировка «бинарники под 3 ОС» в SPEC (M1, §15) меняется на «Linux и Windows, macOS отложен» на шаге B10. Код остаётся кроссплатформенным.

### Адрес контрольного узла

URL контрольного узла, его TLS-адрес, принимающий любой SNI, якоря и нейтральный SNI — компиляционные значения в `cmd/mayak/env.go` (через `runner.Env`). Пока узел не развёрнут, пусты только `defaultControlURL` и `defaultControlAddr`; `ControlTLS` заполняется отдельным разбором `defaultControlAddr`, а не из `ControlClient.BaseURL`. Якоря уже заданы (`https://example.com/`, `https://www.iana.org/`), как и `NeutralSNI="example.net"`; пустой адрес контрольного узла заставляет `mayak check` напечатать, что измерять нечего, и выйти с кодом 2, не трогая сеть. Адреса белых списков (allowlist) в блоке B не заданы, поэтому `allowlist_mode` недостижим, пока владелец их не предоставит.

### Потолки нагрузки

Без изменений по SPEC §5: не больше 4 одновременных проверок, пауза 200–800 мс между стартами, таймаут 8 секунд на тест, 5–20 целей за прогон. Они задаются в одном месте (`internal/runner`, шаг B2) и проверяются тестом, который падает при нарушении. Учёт суммарного трафика одного прогона с лимитом 20 целей переносится вместе с пробами B6/B7 в блок F (Q2); в блоке B эта работа не закрывается.

Проход одной цели (шаг B3, `internal/runner/target.go`) идёт по слоям SPEC §5 и останавливается, когда нижний слой уже решил вердикт: к цели не идёт ни одного запроса, если не прошёл `ctrl`; при неудачном `tcp` не делаются `tls_sni` и `http`; эталон у контрольного узла (`/v1/fetch`) запрашивается только когда `http` получил ответ. Это не ослабляет правила §5: классификатор применяет тот же порядок и возвращает вердикт первого решившего слоя. Один случай — не остановка, а продолжение по правилу 2: когда ответ DNS подменён (`dns_tamper`), `tcp`, `tls_sni` и `http` всё равно идут на доверенный IP, как и велит SPEC («дальнейшие тесты идут по доверенному IP»); вердикт остаётся `dns_tamper`, а их результаты — улики для отчёта.

## «`tls_sni` через контрольный узел»: что говорит SPEC и что делает код

**SPEC, как написано.**

- §5, таблица тестов: «`tls_sni`: два handshake на один IP: с SNI цели и с нейтральным SNI. Выявляет SNI-фильтрацию (обрыв после ClientHello только в первом случае), подмену сертификата».
- §19, таблица «Принято»: «5, `tls_sni`: основной вариант: SNI цели на IP контрольного узла (он принимает любой SNI). Нейтральный SNI на IP цели остаётся второй проверкой, потому что сам сервер цели может отклонить чужой SNI».
- §19, план: «M1: … `tls_sni` через контрольный узел».
- §4: контрольный узел даёт «TLS с любым SNI».

**Как это читается.** Агент делает TLS-рукопожатие с именем цели в SNI, но не на IP цели, а на IP контрольного узла, который стоит вне фильтруемой зоны и принимает любое имя. Если оборудование на пути режет по SNI, оно оборвёт и это рукопожатие, хотя IP заведомо чистый: это и есть основное доказательство SNI-фильтрации. Проверка из §5 (нейтральный SNI на IP цели) становится второй, потому что сам сервер цели может отклонить чужое имя, и её успех или провал не так однозначны.

**Что делает код** (`internal/probe/tls.go`, `internal/classify/classify.go`):

- `TLSSNI` делает три рукопожатия TLS 1.3 одновременно под одним дедлайном 8 секунд: SNI цели на IP цели (`TargetSNI`), нейтральный SNI на IP цели (`NeutralSNI`), SNI цели на IP контрольного узла (`TargetSNIViaControl`, адрес из `TLSSNIRequest.ControlAddr`, порт `TLSPort` = 443).
- Классификатор (`classifyTargetSNIFailure`) объясняет сбой рукопожатия с SNI цели так: если тот же SNI обрывается и на IP контрольного узла, это `sni_block`. Если на IP контрольного узла он проходит, SNI-фильтрация сбой не объясняет (`inconclusive` или `timeout_unknown`). Нейтральный SNI решает только тогда, когда рукопожатие через контрольный узел не делалось.
- Для рукопожатий на IP контрольного узла и с нейтральным SNI `cert_invalid` считается состоявшимся рукопожатием: сертификат узла никогда не выписан на имя цели.

**Вывод.** «`tls_sni` через контрольный узел» в коде уже реализован и совпадает с §19: основная проверка через IP контрольного узла, нейтральный SNI вторая. Новой работы по смыслу теста нет. Для следующих шагов остаются три пробела:

1. **Контрольный узел должен принимать TLS с любым SNI на порту 443.** Это сказано в §4 и §19, но в таблице эндпоинтов §21.1 (`/v1/ping`, `/v1/reach`, `/v1/fetch`) этого слушателя нет. Шаг B8 обязан его сделать, иначе третье рукопожатие всегда упадёт и вердикт `sni_block` через контрольный узел станет недостижим.
2. **Откуда агент берёт IP контрольного узла для третьего рукопожатия.** API узла адресуется URL (`ControlClient.BaseURL`), а `TLSSNIRequest.ControlAddr` требует IP и порт. Если IP получать системным резолвером, провайдер может его исказить (риск из Q1). Решено в B3: это адрес HTTPS-слушателя того же контрольного узла, принимающего любой SNI на порту 443; в `runner.Env` он задан полем `ControlTLS`, а собирает его шаг B5.
3. **Пул сертификатов из `runner.Env` пока нельзя передать в пробы.** В `internal/probe` переопределение корневых сертификатов сделано неэкспортируемыми полями `roots` (в `DNSRequest`, `HTTPRequest`, `CtrlRequest`, `ControlClient`) и неэкспортируемой `tlsSNI`, поэтому `internal/runner` не может подставить сертификат `mockdpi`. Решено в B3: перечисленные запросы получили экспортируемое поле `RootCAs` (nil — системные корни), `TLSSNI` берёт корни из `TLSSNIRequest.RootCAs`, добавлена `DNSAddrCheckRoots`. Это не тестовая лазейка: пул сертификатов прямо входит в среду по Q8.

## Options Considered

Альтернативы рассматривались в плане блока B вместе с вопросами Q1–Q10; здесь записаны только отвергнутые варианты, которые могут всплыть снова:

- **Режим «проверить все цели» и флаг `--host`.** Отвергнуты: нарушают потолок 5–20 целей и правило «только цели из подписанного списка» (SPEC §1, §5).
- **Ненулевой код выхода при вердикте «заблокировано».** Отвергнут: это результат измерения, а не ошибка программы; скрипту хватает кода 2 для «измерить не удалось».
- **Тестовый ключ или переопределение адресов в бинарнике.** Отвергнуто (Q8): лазейка и ловушка для `release-check`.
- **Локализованный вывод.** Отвергнут (Q4): ломается без нужной локали, нужны библиотеки.

## Consequences

- Проще: у шагов B1–B10 одна форма среды, вывода и файлов; тесты команды не требуют сети и root.
- Сложнее: встроенный список устаревает за 30 дней и требует переподписи перед релизом; на реальной сети без развёрнутого `mayak-ctrl` прогон всегда даёт код 2.
- Пересмотреть: в блоке C (несколько контрольных узлов, загрузка списка с сервера), при возврате macOS. Пробы B6/B7 и связанный с ними учёт трафика перенесены в блок F (Q2).
