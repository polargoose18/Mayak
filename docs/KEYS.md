# Ключ подписи списка целей

Агент проверяет только цели из списка, подписанного ed25519 (SPEC, раздел 12). Открытые ключи вшиты в агент: `internal/targets/pubkeys.go`. Подписывает владелец проекта инструментом `cmd/mayak-sign`.

**Сейчас в `pubkeys.go` стоит тестовый ключ, его приватная часть не сохранена. Перед релизом его нужно заменить реальным.** Строка с тестовым ключом помечена `// TESTKEY`: пока метка есть, `make release-check` падает, и CI запускает его на тегах `v*`. Заменяя ключ, удалите строку с меткой, а не только ключ.

## Формат файла

```
{"payload": "<base64 точных байт JSON>", "sig": "<base64 ed25519>"}
```

Подпись считается над **точными байтами** `payload`, ровно как они лежат в файле. Агент сначала проверяет подпись и только потом разбирает JSON; ничего не сериализуется заново. Поэтому порядок полей и пробелы в payload не важны, а любой изменённый байт ломает подпись.

В payload (список целей): `v` (версия формата, сейчас 1), `rev` (`ГГГГ-ММ-ДД.N`), `expires` (RFC 3339), `items`. Правила:

- **Срок действия.** `expires` не в прошлом и не дальше 30 дней от момента подписи. Агент отклоняет истёкший список и список с `expires` дальше 30 дней от его часов. Список надо переподписывать не реже, чем раз в месяц.
- **Откат.** `rev` только растёт: сначала сравнивается дата, потом номер как число (`.10` новее `.9`). Агент хранит последний принятый `rev` и отклоняет меньший. `mayak-sign sign` отказывается подписывать, если в `--out` уже лежит список с таким же или большим `rev`.
- **Версия.** Агент игнорирует поля payload, которых не знает (они подписаны, значит их поставил владелец), но отклоняет `v` больше известной. Несовместимое изменение формата делается поднятием `v`.

## Где хранится приватный ключ

- Вне репозитория и вне сервера, на котором работает `mayakd`. Сервер не подписывает список и не должен иметь доступа к ключу.
- На зашифрованном носителе или в менеджере паролей владельца. Нужна резервная копия в другом месте: потеря ключа без резерва означает смену ключа через релиз агента (см. ниже).
- В репозитории работает защита от случайного коммита: `*.key` и каталог `keys/` в `.gitignore`. Это страховка, а не способ хранения: не кладите ключ в рабочую копию дольше, чем нужно для подписи.

## Кто подписывает

Владелец проекта. Подписанный список (`targets/targets.signed.json`) коммитится в репозиторий; CI (`make sign-check`) проверяет, что он подписан одним из ключей из `pubkeys.go` и соответствует формату. Срок действия при этом не проверяется, чтобы истёкший файл не краснил CI всем остальным изменениям; свежесть списка проверяет агент.

## Как пользоваться

```
go run ./cmd/mayak-sign keygen --out <каталог вне репозитория>
go run ./cmd/mayak-sign pubkey --key <каталог>/targets-signing.key
go run ./cmd/mayak-sign sign --key <каталог>/targets-signing.key \
    --in targets/targets.json --out targets/targets.signed.json
go run ./cmd/mayak-sign verify --pub <открытый ключ base64> --in targets/targets.signed.json
```

`keygen` пишет приватный ключ с правами 0600, ничего не перезаписывает и печатает открытый ключ в base64. Открытый ключ можно получить из файла приватного ключа в любой момент: `pubkey` печатает ту же строку (одну, без ничего лишнего), которую принимает `verify --pub` и которая нужна в `pubkeys.go`. Приватный ключ он не выводит, а если у файла права шире 0600, печатает предупреждение в stderr. `sign` берёт `rev` и `expires` из входного файла, проверяет список теми же правилами, что и агент, и подписывает байты входного файла как есть. Он не подпишет список с истёкшим или слишком далёким `expires`, а также не перезапишет в `--out` файл, который не является подписанным списком. Если у файла ключа права шире 0600, он печатает предупреждение.

Входной файл `targets/targets.json` — это сам payload (без обёртки и подписи). Образец: `targets/targets.example.payload.json`; в `targets/targets.example.json` он же в виде файла с подписью (подпись фиктивная).

## Как менять ключ

Агент принимает подпись любого из вшитых ключей, поэтому смена идёт в три шага. Нарушать порядок нельзя: агенты, которые ещё не обновились, не примут список с новым ключом.

1. Создать новую пару (`keygen`), добавить **второй** открытый ключ в `pubkeys.go` и выпустить релиз агента. Список пока подписан старым ключом.
2. Дождаться, пока релиз получит достаточная часть пользователей, и подписать список **новым** ключом.
3. В следующем релизе удалить старый открытый ключ из `pubkeys.go`, а старый приватный ключ уничтожить.

## Что делать при утечке приватного ключа

Тот, у кого есть ключ, может подписать произвольный список целей, и агенты его примут. Отозвать открытый ключ удалённо нельзя: он вшит в бинарник, поэтому отзыв работает только через релиз.

1. Немедленно прекратить подписывать список старым ключом и сообщить об утечке пользователям (README, канал проекта).
2. Создать новую пару и выпустить релиз, в котором **старый ключ заменён** новым. Это не плановая смена из трёх шагов: оставлять скомпрометированный ключ в списке доверенных нельзя.
3. Подписать актуальный список новым ключом.
4. Выяснить, как ключ попал в чужие руки, и проверить подписанные списки, выпущенные за это время.
5. Пока пользователь не обновил агент, его агент продолжает доверять скомпрометированному ключу. Защита от этого — только быстрое обновление.

Рекомендация: ключ подписи списка не должен совпадать с ключом подписи релизов агента (minisign или cosign, SPEC, раздел 12). Тогда утечка одного не ставит под угрозу другой.
