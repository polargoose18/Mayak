# ADR-004: Модель угроз анонимности

**Status:** Accepted
**Date:** 2026-10-13
**Deciders:** владелец проекта (решение принято 2026-10-13)

## Context

SPEC v0.1 обещает: нет IP в отчёте, нет идентификатора установки, отчёты одного агента нельзя связать. Внешнее ревью показало, что часть обещаний держится на слове оператора, а не на устройстве системы:

- сервер видит IP при приёме, и «забываем IP» не проверяется снаружи;
- провайдер видит сам факт участия в «Маяке»;
- контрольный узел видит IP всех проб;
- метаданные отчёта (ОС, версия, время, ASN) в малых ASN почти идентифицируют человека.

Дополнительно: сейчас проект ведёт один человек и держит все компоненты сам (шлюз, контрольный узел, релей, если он появится). Второго оператора нет. Поэтому разделение «релей не видит содержимого, шлюз не видит IP» формальное, пока оба у одного владельца.

## Decision

Гарантии вводятся по этапам. Проект обещает только то, что реально обеспечено на текущем этапе, и README говорит это прямо.

| Этап | Что обеспечено | Чем обеспечено |
|---|---|---|
| Запуск (M6) | Нет IP в отчёте и в базе; нет идентификатора установки; нет логов с адресами; подписанный список целей | Политика оператора, открытый код, тесты «IP не оседает». Проверить извне это нельзя |
| Появился второй оператор | Шлюз не видит IP, релей не видит содержимое | OHTTP (RFC 9458), если релей держит другой оператор |
| Позже (M7, по необходимости) | Отчёты разных окон нельзя связать; один голос на окно | Анонимные учётные данные (ADR-005) |

Угрозы на этапе запуска:

| Противник | Что видит | Гарантируем | Не гарантируем |
|---|---|---|---|
| Провайдер пользователя | Соединения с сервером «Маяка», их время и объём | Содержимое отчётов скрыто TLS | Что факт участия не виден; снижаем: отложенная отправка 0–15 минут, общий домен |
| Оператор шлюза (он же всё остальное) | IP при приёме, содержимое отчёта | IP не записывается и не хранится; в базе только агрегируемые поля и `src_bucket` с суточной солью | Что сервер не начнёт логировать незаметно: проверить это можно только по открытому коду и честности оператора |
| Контрольный узел | IP проб, SNI проверок | Политика «без логов», тест «IP не оседает», в перспективе несколько узлов у разных операторов | Что узел не будет скомпрометирован |
| Внешний атакующий (сибилы) | Публичные данные | Токены Privacy Pass ограничивают частоту; потолок веса одного `src_bucket`; кворум; малый вес веб-пробы | Что нельзя накопить много проб деньгами и временем |
| Принуждение оператора (суд, изъятие) | Содержимое базы | Нечего выдавать сверх агрегатов и 14 дней обезличенных строк | Что агрегаты малых ASN ничего не раскрывают |
| Компрометация ключей | Возможность подмены списка целей и обновлений | Подпись ed25519, подписанные релизы | Что компрометация будет замечена сразу |

**Не цели:** защита от глобального пассивного наблюдателя; скрытие факта участия от провайдера; защита от пользователя, который сам публикует свой отчёт.

**Принятые параметры:**

1. Ячейка (оператор × сервис) публикуется только при числе разных источников не менее **k = 5**.
2. Пробы отправляют отчёты со **случайной задержкой 0–15 минут**. Статус может отставать от реальности до 15 минут; для карты, а не сигнализации, это допустимо.
3. Метаданные огрубляются: `os` до семейства, `ver` до minor; `region` не отправляется по умолчанию.
4. Размер запроса выравнивается.
5. Принцип 2 в SPEC на этапе запуска: «в отчёте нет идентификатора установки; `report_id` случаен, и связать два отчёта по нему нельзя; шлюз видит IP на время приёма и не сохраняет его». Формулировка про учётные данные добавляется вместе с M7.

## Options Considered

### Option A: обещания оператора и поэтапное усиление (выбран)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Низкая на старте, растёт по мере усиления |
| Cost | Низкая |
| Scalability | Не зависит от схемы |
| Trust required | На старте полное доверие оператору; снижается по этапам |

**Pros:** можно запускаться без второго оператора и без Rust. **Cons:** на старте приватность не проверяется извне.

### Option B: техническая гарантия с первого дня (OHTTP + учётные данные)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Высокая |
| Cost | Второй оператор, Rust-зависимость |
| Scalability | Приемлемая |
| Trust required | Честность хотя бы одного из релея и шлюза |

**Pros:** гарантии держатся на устройстве системы. **Cons:** при одном владельце релея и шлюза смысла нет, а сложность реальна.

## Trade-off Analysis

Для пет-проекта без пользователей главный риск — не выйти из разработки. Поэтому сначала запуск с честной оговоркой, потом усиление. Это не отменяет требования ревью: анонимность остаётся целью, но не блокирует выход.

## Consequences

- Проще: запуск без второго оператора; честный README.
- Сложнее: на этапе запуска пользователи вынуждены доверять оператору; нужно написать это явно.
- Пересмотреть: когда появится второй оператор; когда появится реальное число проб; после первого внешнего аудита.
